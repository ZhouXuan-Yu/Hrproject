# 招聘数据契约与匹配逻辑修复方案

> 状态：实施中  
> 基线：Java 业务后端 `hr-backend-new` + Python AI 服务 + Vue 前端  
> 目标：让页面展示的数据来源、接口字段和招聘业务语义一致，并确保员工只能访问授权范围内的信息。

## 1. 已确认的现状

### 1.1 招聘基础配置 / 渠道配置

- 前端 `RecruitConfig.vue` 通过 `/api/config/channels` 请求渠道列表，没有渠道列表的前端 Mock 回退。
- Java 后端 `ConfigService` 从 `t_hr_recruit_channel` 读取渠道名称、启用状态和类型。
- 渠道成本来自 `t_hr_system_config.channel_costs`，未配置时才使用代码中的默认成本字典。
- 因此页面当前渠道数据是数据库数据经过接口映射后的结果；若请求失败，页面应显示为空，而不是伪造一份渠道列表。

### 1.2 人才库的岗位字段

- `t_hr_recruit_process` 关联的是候选人已经进入的招聘需求，属于“已匹配/已进入流程的岗位”。
- 简历抽取结果中的 `target_position` 才是候选人的原始应聘岗位。
- 旧实现把关联需求的第一个岗位写回 `targetPosition`，前端再用同一列展示，导致“投递岗位”被“匹配岗位”覆盖。

### 1.3 内部员工库

- 后端只有在 `tab=internal` 时才返回员工列表。
- 前端原来只请求默认的外部候选人列表，却试图从同一响应中读取 `int/internal` 字段。
- 后端返回的是 `score`、`tags` 等结构化字段，前端却读取 `scoreHtml`、`matchHtml`、`tagsHtml`，属于迁移后的接口契约不一致。

### 1.4 员工数据权限

- `DataScopeService` 已定义 `all / dept / dept_and_self / self / none` 五种范围。
- 原有人才库员工列表和员工详情没有应用该范围；前端隐藏菜单不能替代后端鉴权。
- 目标口径：管理员、HR、总监按有效数据范围查看；部门负责人至少只能看本部门；普通员工默认只能看自己，并提供本人档案入口。

### 1.5 候选人匹配

- 需求详情的匹配分当前使用学历、学校、工作年限等候选人字段，但 JD 技能命中仍是固定分，匹配理由也是固定文案。
- “重新匹配”当前会直接把高分候选人写入招聘流程，预览和提交没有分开，容易造成误操作。
- 内部员工匹配当前把岗位选项硬编码为 `java/frontend/pm/data`，后端分数由 `demandId + employeeId` 的 hash 生成，不是真实业务匹配。

## 2. 目标数据契约

### 2.1 候选人列表

候选人对象同时保留以下两个概念，禁止互相覆盖：

```json
{
  "appliedPosition": "候选人原始应聘岗位",
  "linkedDemands": [
    {
      "demandNo": "REQ-001",
      "position": "已关联的招聘需求岗位",
      "matchScore": 82
    }
  ]
}
```

- `appliedPosition`：来自简历结构化数据或候选人正式投递记录。
- `linkedDemands`：来自招聘流程和匹配记录，可有多个。
- `targetPosition` 仅作为兼容旧前端的过渡字段，不再作为业务主字段。

### 2.2 内部员工列表

前端只消费结构化数据，不使用后端拼接 HTML：

```json
{
  "id": "EMP001",
  "name": "员工姓名",
  "dept": "部门",
  "pos": "当前岗位",
  "score": 86.5,
  "perf": "A",
  "tags": ["Java", "架构"],
  "transfer": true
}
```

接口：`GET /api/talent/list?tab=internal&page=1&pageSize=20`。

### 2.3 员工本人信息

- 增加 `GET /api/talent/me`，返回当前登录用户关联的员工档案。
- `GET /api/talent/employee/{id}` 和 `GET /api/talent/list?tab=internal` 必须在服务端执行数据范围过滤。
- 员工角色不应因为前端路由隐藏而获得候选人库、联系方式或简历原件权限。

### 2.4 匹配结果

匹配结果必须说明来源和分项依据，至少包含：

- 需求编号、岗位、需求版本；
- 候选人或员工的实际学历、年限、技能、城市、薪资、绩效、可调岗状态；
- 分项得分、硬性不满足项、最终分数和算法版本。

后续将把“匹配预览”和“提交到招聘流程”拆成两个动作，预览不写入流程，提交只写入用户明确选择的候选人。

## 3. 实施顺序

### 第一阶段：接口契约和岗位语义（本轮）

1. 前端独立请求内部员工列表并适配后端真实结构化字段。
2. 候选人列表区分“应聘岗位”和“已匹配岗位”。
3. 内部匹配岗位选项改为真实需求列表，移除硬编码岗位值。

### 第二阶段：数据权限和本人档案（本轮优先修复）

1. 将 `DataScopeService` 接入员工列表和详情。
2. 增加 `/api/talent/me`，为员工提供只读本人档案。
3. 对人才库操作接口补齐角色边界，联系方式和简历原件继续保持 HR 级别限制。

### 第三阶段：真实匹配和可审计提交

1. 用真实需求字段和员工档案计算内部匹配分，并返回分项说明。
2. 用候选人简历技能与需求技能进行命中计算，去除固定 JD 分和固定理由。
3. 增加 `preview/commit` 两阶段接口，记录算法版本、输入快照和结果明细。

## 4. 验收标准

- 渠道配置页面的每条数据都能追溯到 `/api/config/channels` 或明确的系统默认成本配置。
- 候选人同时有原始应聘岗位和已匹配岗位时，两者在页面分开显示。
- 内部员工 tab 能真实加载 `/api/talent/list?tab=internal`，不再依赖 `int/internal` 混合响应或 HTML 字段。
- 普通员工访问员工库时只能看到自己，访问其他员工详情返回 403；`/api/talent/me` 返回自己的档案。
- 内部匹配的岗位下拉来自招聘需求接口，不出现 `java/frontend/pm/data` 等硬编码值。
- 匹配结果能展示真实数据来源和分项说明；预览不会自动创建招聘流程。
- Java 后端单元/编译检查通过，前端构建通过，Docker 中的 Java、Python、Redis 服务健康检查通过。

## 5. 数据迁移注意事项

- 不直接覆盖现有候选人数据。
- 如后续确认需要稳定保存原始应聘岗位，再新增 nullable 的 `target_position` 字段，并仅从现有简历抽取 JSON 回填有值记录。
- 保留现有工作树中与本次问题无关的用户修改，不做强制清理。

## 6. 本轮已实施

- `TalentService` 输出 `appliedPosition`，不再用已关联需求覆盖原始应聘岗位。
- 人才库前端拆分显示“应聘岗位”和“已匹配岗位”。
- 内部员工库独立请求 `tab=internal`，前端改用 `score`、`tags` 等结构化字段。
- 员工列表、员工详情接入 `DataScopeService`，新增 `/api/talent/me`。
- 内部匹配岗位改为真实需求列表，后端按需求和员工档案计算分项分数，不再使用 hash 伪随机分。
- 增加需求匹配预览接口 `/api/demand/{id}/match/preview`；需求详情的“重新匹配”改为只预览，不自动创建招聘流程。
- 候选人匹配分移除固定 JD 基础分和哈希扰动，开始使用简历技能与需求必备/加分技能字段计算命中。

后续仍需补充：匹配预览结果的人工确认提交接口、候选人匹配明细的技能证据展示，以及当历史简历没有技能抽取结果时的补录提示。
